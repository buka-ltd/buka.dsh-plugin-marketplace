# ADR 0022：助理是工作流的点名，代办失败即作业失败

- 状态：已采纳（2026-11-17）；取代 ADR 0010 第 3 条（助理带标记）与第 6 条（失败回到待认领）
- 影响面：Workers 的登记表、路由、工具与页面；Workflows 的定义校验、调度、交回方式与页面；术语表与文档

## 背景

人任务类型本来就能点名一个智能体代办：任务就绪后引擎启动它的会话，把任务交给它，它代人点动作完成。但同一件事还有第二道门——那个智能体必须在 Workers 里被标记成「助理」，否则保存定义时直接被拒绝。

两处说的是同一件事，一处是工作流的结构，一处是打工人身上的属性。打工人并不知道自己会被哪个工作流点名，这个标记也回答不了「它替我办的是哪类任务」；它只是同一份信息存了两遍，两边还得手工保持一致。

## 决定

1. **打工人不再有助理标记。** 登记表升到 version 4，迁移时丢掉 `assistant` 字段；`POST /buka-workers/assistant` 路由、`buka_worker_build` 与 `buka_workers` 输出里的 `assistant`、Workers 页面的徽标 / 开关 / 「只看助理」筛选一并删除。
2. **助理是被工作流点名的智能体。** 人任务类型用 `assistant` 点名代办这类任务（存标识符）；交回方式用 `delivery.kind = "assistant"` 点名代收最终报告。校验只要求被点名的标识符存在且 `driver: "agent"`，不再看任何标记；新建作业时列出全部智能体供选择。
3. **代办失败即作业失败。** 被点名的智能体接手后没交出结果（会话结束、超时、无法恢复），任务标失败，作业直接进 `failed`，其余在跑任务取消；不再回到「待认领」，人不能接手。取代 ADR 0010 第 6 条。
4. **页面只说两件事：是不是给人的任务，谁代办。** 任务抽屉与看板卡片去掉「承办者」这一行与这个词；人任务显示「代办：某人」或「待你办理 / 你在办理」，打工人任务只显示执行者。任务记录里「谁接走、是不是代办」仍然保存，供调度、提示词与执行记录使用。

## 后果

- 失败作业不再是死路：两种重启方式见 ADR 0023。
- 定义格式不变（`assistant` 字段本来就有），旧定义不需要迁移：以前能保存的定义都点过名、也都带过标记，删掉标记要求后照样合法。
- 已存作业快照保留原字段，读取时照旧显示。
- 失败比「任务失败、作业继续」更严厉，是刻意的：代办代表人的决策，没交出结果就说明这个作业的结果不可信，不能悄悄降级成人工处理。
