# ADR 0024：执行提示按作者拆分投递身份

- 状态：部分被 ADR 0033 取代（2026-11-24）：定义改为模板，任务内容与定义一起按用户身份投递；按作者拆分投递身份的原则保留
- 影响面：workers 的 `dispatchSession`、workflows 的执行提示词、ADR 0017 / 0018 的提示词投递部分

## 背景

一次 agent 派发的执行提示只有三段，但三段的作者不同：

- 工作流规则由插件生成；
- 任务类型的 `definition` 由流程维护者写；
- 任务内容可能来自表单，也可能由上游 agent 通过 `buka_task_create` 写入。

过去三段拼成一条消息，workers 用 `followup` 投递，来源是 `buka-worker`。DSH 宿主只在 `source.kind === 'user'` 的消息里识别 `/skill-name` 手势——这也是 `disable-model-invocation: true` skill 的唯一入口。于是流程维护者写在定义里的 `/grill-with-docs` 只是普通文字，对应 skill 不会被加载。

不能把整条提示都改成用户来源：任务内容会因此获得用户身份，上游 agent 就能借 `/xxx` 冒充用户触发 skill。

## 决定

1. **按作者拆分投递身份**：
   - 上下文消息：工作流规则 + 任务内容，用 `inject` 投递到下一个 step，来源不是 `user`（`buka-worker`），不唤醒会话；
   - 用户消息：任务类型的 `definition`，用 `followup` 投递，来源是 `user`，唤醒这一次执行。
2. **先 `inject` 后 `followup`**：两者在同一步被领取，上下文先于用户消息进入请求。
3. **任务内容永远不进用户消息**：无论它来自表单还是上游 agent，都留在非用户来源的上下文里。
4. **没有定义时退化**：不产生空的用户消息，仍只发一条 `followup`，来源 `buka-worker`，行为与旧版一致。
5. **落盘仍是完整文本**：`prompts/<attempt>.md` 保存「规则 + 定义 + 内容」，顺序不变，供排查使用。
6. **只有 agent 任务拆分**：助理任务、恢复路径（`openSession` / `send`）与 plan 模式的投递保持原样。
7. **接口**：workers 的 `WorkerDispatchRequest` 新增可选 `userPrompt`；workflows 用 `buildExecutionPromptSections()` 提供拆分结果，`claimAgentTask()` / `launchAgent()` 把 `userPrompt` 一路传给 `dispatchSession()`。

## 后果

- 任务类型定义里的 `/skill-name` 现在能生效，且不需要把任务内容或工作流规则也提权成用户输入。
- 定义与内容在会话里的到达顺序变成「上下文（规则 + 内容）→ 用户消息（定义）」，与落盘文件的段落顺序不同；排查时以 prompt 文件与两条消息的来源为准。
- 拆分只发生在派发入口；如需在其他入口使用用户身份投递，应显式传 `userPrompt`，不要放宽任务内容的来源。
- 定义不再与规则、内容拼在一条消息里，模型看到的是两条相邻消息；这依赖宿主在同一步先领 `inject`、再领 `followup`。
