# ADR 0015：通道取代边，定义升到 v5

- 状态：已采纳（2026-11-13）
- 影响面：工作流定义格式、任务创建、校验、存储迁移、界面、执行 prompt

## 背景

v4 规格 §5.5 明确写了「边上不写 prompt / name / tone」，边只有 `from / to / types / back`，同一对节点只允许一条。实践下来有三个问题：

1. 边无法被引用。图里只能显示「研发 → 测试」，报错只能给 `edges[2]`，人无法说「把返工那条边关掉」，agent 也无法在定义里稳定指认一条边。
2. 同一对节点之间只有一条边，被迫用任务类型白名单表达「A 能派哪几种任务」。当同一对协作者需要多条语义不同的路线（提测、加急提测、补料），类型白名单和 label 都无处安放。
3. 任务不记录自己依据哪条路线抵达，作业过程只能看到「谁创建了谁」，看不到「依据什么」。

v4 的禁令是为了防止边变成管道：边一旦承载 prompt / 条件 / 顺序，任务就不再是按岗位派发，而是在边上流动。这条不变量必须保留，但它不需要以「边不能有名字」为代价。

## 决定

1. **边升级为「通道」**：`{ id, label, from, to, types?, back? }`。`id` 工作流内唯一、小写点分；`label` 必填、自由文本、不要求唯一。`label` 只给人 / agent 读，引擎永不参与判定。
2. **同一对节点可以有多条通道**，`types` 可以重叠，不再要求「一个类型只走一条通道」。
3. **派发以通道为单位**：`buka_task_create` 只传 `channel`，不再传 `position`；`start.next` 条目用 `channel` 代替 `position`；目标岗位由通道的 `to` 推出。每个任务（启动任务除外）记录 `channel`；通道必须从创建者岗位出发、终点是目标岗位、允许该任务类型。
4. **`back` 语义不变**：显式回向、必须闭合环、每个环至少一条回向通道；同一对有序节点的 `back` 必须一致。
5. **指向 `end` 的通道不允许 `types`**，可以有多条；结束任务的 payload 契约仍由 `end.task` 唯一决定。
6. **v4 → v5 一次性迁移**：`id` 派生为 `<from>.<to>`，`label` 派生为端点显示名（`研发 → 测试`）；作业快照同迁；任务按 v4 的唯一边回填 `channel`；v4 类型不再保留。
7. **点名推翻 v4 规格「边上不写 name」**：`label` 与 `id` 是管理 / 沟通面，不是执行面。

## 后果

- 「通道是权限，不是管道」仍然成立：引擎只校验通道的起点、终点与类型白名单，`label` 不参与判定；任务不会沿着通道「流动」，通道也不承载状态、prompt 或条件。
- 过程可追溯：任务记录自己走的通道，流程图能点亮具体那条路线，执行 prompt 会说明「你由『返工』从测试派发而来」。
- 图渲染要处理并行通道：同一对节点的多条线需要车道偏移与标签避让。
- 旧会话的 prompt 里没有通道概念，调用任务创建会报错并列出候选；迁移后定义都是 v5，重试即可，这是「通道必填」的代价。
- 回边、预算、显式依赖的规则全部不变。
