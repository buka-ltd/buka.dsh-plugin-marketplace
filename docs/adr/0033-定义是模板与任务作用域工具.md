# ADR 0033：任务类型的定义是模板，执行提示按「规则 + 用户消息」投递

- 状态：已采纳（2026-11-24）
- 影响面：workflows 的定义格式与校验（v8 → v9）、执行提示组装、引擎派发与恢复、按任务注册的工具、ADR 0024 / ADR 0017 的投递部分、中英 DETAIL、README、GLOSSARY、编排 preset、插件版本（4.0.0 → 5.0.0）

## 背景

ADR 0024 按作者把一次 agent 派发拆成两条消息：上下文（`buka-worker`：工作流规则 + 任务内容）与用户消息（`user`：任务类型的定义原文）。它解决了「定义里的 `/skill-name` 不该被当成普通文字」，但把两类东西放反了：

- **定义只能是一段静态文字。** 它引用不到这张任务的数据。例如 `dev.implement` 写「先使用 /grill-with-docs，基于收集到的需求资料逐项追问」，需求资料却在另一条消息里，模型要自己把两条消息对上；定义越写越像给「两条消息」写的说明书。
- **任务内容放错了身份。** 它是这一次的具体指令，却和引擎规则一起以 `buka-worker` 身份进入会话。
- **工具的必要信息不在工具上。** 能创建什么 task、人任务有哪些动作，执行者要先调 `buka_task_targets` / `buka_task_actions` 才知道，常常不知道 `buka_task_create` / `buka_task_complete` 该传什么。
- **plan 模式与助理任务各有一套投递形态。** plan 模式把用户消息置空、退回单条 followup；助理任务把规则、定义、内容拼成一整条。两者都与它们的语义无关。

## 决定

1. **定义升到 v9，`definition` 是模板。** 执行时 `renderTemplate(definition, { content: task.content }, { escape: true })`，渲染结果就是以 `user` 身份投递的那条消息。只认 `{{content}}`（整份内容，对象按 JSON）与 `{{content.<path>}}`，沿用模板引擎的严格取值与末尾 `?` 可选写法。
2. **保存时校验模板。** 路径必须在本任务类型的任务内容 schema 里声明；经过非必填字段的路径必须写 `?`，否则拒绝并给出正确写法；`{{input.*}}` / `{{nodes.*}}` 一律拒绝。定义省略时，用户消息是转义后的整份任务内容（空内容也有非空文本）。运行期取不到必填路径时任务失败，错误写明路径。内建结束任务的定义是固定文案 + `{{content}}`。
3. **代入值不触发 skill 手势。** 代入值在 `(^|\s)/` 之后插入零宽空格（U+200B），宿主 `dsh-tool-skill` 的 `SKILL_GESTURE` 因此不再匹配，界面看起来不变；模板原文不转义。测试用同一条正则钉住这个行为——宿主改规则时测试先失败。
4. **上下文只给工作流的基础信息。** `buka-worker` 上下文只保留工作流规则（只列工具能力）与工作树规则（仅 `worktree` 不是 `none` 时出现）。工作流名称、描述、岗位、作业编号、通道、定义与任务内容都不进上下文。
5. **工具的必要信息写进工具说明。** 任务会话 `agent/created` 时，按这条会话执行的任务，在 agent 作用域（`createScope(agent.ctx, agent)`）里各注册一份 `buka_task_create`（列出可创建 target、展示名与 content schema）与 `buka_task_complete`（人任务列出动作 id、展示名与 input schema）。作用域内的注册遮蔽同名全局工具，其它会话仍看到通用说明；会话释放或插件卸载时撤销。删除 `buka_task_targets` 与 `buka_task_actions`。引擎在 `dispatchSession` / `openSession` 之前先绑定会话与任务（恢复路径也一样），所以 `agent/created` 时已经查得到任务。
6. **plan 模式只是会话模式。** 投递与普通任务相同（上下文 + 用户消息）；`planMode` 会话标志保持。
7. **助理任务的提示词固定。** 「请你负责对接任务「<任务类型>」（<任务 id>）的处理人，并严格执行处理人对于该任务的决策。」以 `buka-worker` 来源单条投递；任务内容用 `buka_task_get` 读，动作见 `buka_task_complete` 的说明。
8. **不兼容，不做自动迁移。** 纯文字定义无法机械地改成模板：v8 工作流标「待升级」，不能启动新作业，由编排预设（AI）按 v9 改写后保存新版本。进行中的 v8 作业按快照版本走旧语义（上下文带内容、用户消息是定义原文）跑完。
9. **落盘。** `prompts/<attempt>.md` 保存「上下文 + 用户消息」，顺序与到达顺序一致。

## 备选与否决理由

- **保留 ADR 0024 的两条消息，只把任务内容挪进用户消息。** 定义仍然引用不到任务内容，模型仍要自己对齐两条消息；而定义才是「这一次怎么做」该展开的地方。
- **把内容直接拼进定义（不经模板校验）。** 路径写错要到运行时才暴露，而且 `{{input.*}}` / `{{nodes.*}}` 会混进来；保存时校验一次更便宜。
- **v8 → v9 自动迁移。** 纯文字定义没有可推导的模板位置，自动改写只会猜；与其生成半对的定义，不如让编排预设逐份重写并让人看见新版本。
- **继续保留 `buka_task_targets` / `buka_task_actions`。** 一次性读的工具信息本来就属于「调用这个工具需要知道什么」，放在工具说明里少一次往返，也让作用域遮蔽成为自然的分层。
- **把任务内容转义后写回存储。** 会让存储里的内容与用户输入不一致，排查时误导；只在渲染出的提示里转义，存储保持原样。
- **在 workers 服务里注册工具。** workers 只负责会话与轮次；「这条会话在执行哪张任务」是引擎的知识，注册留在 workflows 的 Host 一侧。

## 后果

- 所有 v8 工作流在升级后都不能再启动新作业，直到改写为 v9；运行中的 v8 作业照常跑完。
- 防伪造 skill 从「靠来源隔离（内容留在非用户消息）」变成「靠转义」，依赖宿主的 `SKILL_GESTURE` 正则保持不变；测试会把这条依赖钉住。
- 故意写在任务内容或表单里的 `/skill-name` 不再生效——需要触发 skill 的指令属于任务类型的定义（模板原文），不属于这一次的数据。
- 删掉两个工具后，执行者的工具清单更短，创建 / 完成工具自带本任务的 target 与动作说明。
- 中英 DETAIL、README、GLOSSARY 的「任务类型的定义」「任务内容」、`buka_workflow_save` 的定义帮助、编排 preset 与 ADR 0024 / 0017 的投递部分都要同步。
