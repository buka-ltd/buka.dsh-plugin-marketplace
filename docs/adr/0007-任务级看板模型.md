# ADR 0007：任务级看板模型

- 状态：已采纳（2026-11-12）
- 影响面：workflows 的引擎、看板、页面；图可视化

## 背景

旧模型是「单活跃节点 + join 屏障」的流水线：等待落在节点上，测试必须等研发节点开工才能做准备工作；任务不是独立实体，页面只能观测。目标是用结构控制风险，用看板控制吞吐。

## 决定

1. **任务是最小执行单元。** 任务是看板上的卡，也是执行器的工作单位；它属于一个岗位和一个任务类型。
2. **岗位 = 执行者 + 任务类型契约。** 图里的节点（除内建开始 / 结束）都是岗位；一个岗位一种执行者。
3. **边是权限，不是管道。** 边表示「谁可以把任务派给谁」，可带任务类型白名单；回边必须显式标注。任务记录带目标岗位，引擎校验边存在。
4. **等待落在任务上。** 任务的条件是它声明的依赖；节点没有「开工 / 等批次」的动作；没有 join 节点。
5. **任务由执行中的执行者创建，可多次添加。** 不要求执行结束才产出 `tasks[]`；没有批次 / 代次。
6. **看板行 = 岗位，列 = 任务状态**（排队 / 待认领 / 进行中 / 已完成 / 异常）；作业详情保留 DAG 视图（复用 `graph.ts`）。
7. **并发由执行者实例决定。** v1 agent 机器人岗位一个实例，program 机器人按其驱动并发，人岗位不占机器人实例。

## 后果

- supervisor / run-store / 定义校验 / 工具 / 页面基本重写；`graph.ts`、`output.ts`、`template.ts`、附件安全逻辑保留。
- 看板成为写操作页面：认领、重试、取消、审阅。
- 任务依赖图天然无环（只指向已创建任务），工作流图允许环。
