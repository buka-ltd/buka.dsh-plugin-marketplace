# ADR 0019：机器人任务完成后创建后续任务

- 状态：已采纳（2026-11-16）
- 影响面：workflows 的定义格式、校验、引擎、页面与文档；不改存储结构、不升定义版本

## 背景

v7 的任务创建只发生在「活着的创建者」手里：开始节点的 `next`、人任务的动作、以及执行中的 agent 调 `buka_task_create`。机器人（`ProgramDriver`）没有会话、没有工具，完成时只写入结果与状态，不会创建任何任务。

于是 `clock` 只能当终点：作业以 clock 等待开头时，等待结束后没有任务可以接手，作业会以「no end task was completed」结算失败。要表达「到点之后执行」，只能在等待前面塞一个 agent 任务，由它先建 clock、再建带依赖的执行任务——多一步，而且人任务动作根本做不到。

另一种想法是让程序在执行后自己创建任务。这会绕开「结构在定义、内容给执行者」的分界：任务往哪走、走哪条通道属于工作流定义，不该藏在驱动代码或任务内容里。

## 决定

1. **任务类型新增可选 `creates`，只对机器人岗位有效。**
   - 形状复用 `CreationDefinition`（`channel` + `type` + `content`），与人任务动作的 `creates` 一致；一个任务类型可以声明多条，也可以一条都不声明。
   - agent 任务继续用工具动态创建，人任务继续用动作；非机器人岗位声明 `creates` 在保存时拒绝。
2. **触发点固定为「机器人成功完成任务之后」。**
   - 引擎在机器人完成的同一段作业锁里，先按顺序渲染并校验全部创建，再逐条创建，最后完成任务并重算调度。
   - 创建的任务依赖刚完成的任务；机器人完成前它们保持 `pending`，完成后同一轮提升为 `ready`。
   - 机器人失败、取消、状态已不是 `running` 时不创建。
3. **模板只认 `{{content.*}}`。** 机器人没有动作表单，`{{input.*}}` 在保存工作流时就拒绝；结果文本不参与创建，保持「结果不进流程」。
4. **创建失败让机器人任务失败。** 内容、通道、任务类型、预算或打工人登记不合法时，机器人任务以 `program task failed: <原因>` 失败；已经插入的任务保留，行为与现有动作提交路径一致。
5. **定义格式只在 v7 上追加字段。** 不升版本、不迁移；旧定义与旧作业不受影响。
6. **人任务动作与机器人完成共用同一段创建实现**（`createDeclaredLocked`），避免两条路径各写一遍渲染、校验与事件。

## 后果

- `clock` 可以在到点后自动放行真正的执行任务，「先等到点、再执行」从作业起点就能表达。
- 页面任务类型卡片多一行「完成后创建」，列出目标类型与通道。
- 创建之间不能互相声明依赖；需要跨创建排序时再单独设计（不引入符号 id）。
- 恢复窗口：若宿主机在「插入创建任务」与「完成任务」之间崩溃，重启后程序会重新完成，可能重复创建。这与现行动作路径同一窗口，本次不引入幂等任务 id，作为已知限制记录。
- 机器人仍然是「接收内容、返回文本」的固定程序；它不知道通道，也不持有创建逻辑。
