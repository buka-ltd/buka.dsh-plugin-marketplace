# ADR 0002：用一次性大改完成迁移，分两批提交

- 状态：已采纳（2026-11-12）
- 影响面：全部插件、CI

## 背景

四个插件合计约 25k 行手写 JavaScript，没有类型、没有共享层、没有结构约束。
用户选择"一次性全部改成 TypeScript、一次发布"，而不是逐个插件灰度。

## 决定

**在一个分支上一次性改完，合并后发一次版。** 但提交拆成两批，让每个 commit 仍然只做一件事：

1. **第一批：纯语言迁移。** 文件按 1:1 搬，只加类型、改 import，行为零变化。
2. **第二批：结构改动。** 抽 `packages/plugin-kit` 与 `packages/plugin-ui`、拆 god module、
   修 `join` 节点、文案单一来源、兼容范围、版本号。

## 为什么不是直接在主分支上增量推进

主分支每推一次，CI 就重建索引并发布到 Pages（`.github/workflows/market.yml` 的 `deploy`）。
也就是说主分支上任何中间提交都会立刻变成用户能装到的插件。改成"一半是 TypeScript、
产物可能还没重建"的中间态，用户装到的就是坏插件。所以：

- 迁移期间主分支一动不动，用户装的仍是旧版本；
- 全部改完、装进临时 profile 验证通过后一次性合并。

## 为什么提交要分两批

"换语言"本身已经足够危险：25k 行手工改写，出错时要把范围缩到最小。
如果同一批提交里还在拆文件、抽公共包、修 bug，出现回归时无法判断是哪一类改动引起的，
`git bisect` 也失去意义。分成两批后，第一批的 diff 可以逐行对照原 JS。

## 验证方式

- 每个插件过质量门：`tsc -p` 零错误、`biome check` 干净、`node --test` 全量通过、
  连续两次构建产物 sha 一致。
- 打包后用假 `window.__ModuleLoader__` 执行 `lib/client.js`，确认 `id` / `inject` / `apply` 正确。
- 装进临时 profile，`--dump-config` 确认补丁行进入 composition、`Config` 默认值被解析。

## 后果

- 迁移期间不能并发开发新功能，否则冲突不断。
- 合并后 CI 多出三步：类型检查、打包、产物一致性检查。
- 仓库开始有 `pnpm install` 这一步依赖（此前零依赖）。
