# ADR 0017：执行提示词只暴露任务，定义升到 v6

- 状态：部分被 ADR 0018 取代（2026-11-14）：提示词段数与人任务的结果契约已作废
- 影响面：工作流定义格式、执行提示词、任务创建工具、存储迁移、页面、编排 preset

## 背景

v5 的执行提示词是「把引擎知道的一切都告诉执行者」：

- 作业编号与工作流名、入站通道、来源岗位；
- 岗位与任务类型的 label / id / description；
- 依赖任务结果、可见附件清单、附件工作目录；
- 可派发通道清单（通道 id、目标岗位、类型白名单）；
- 只读工具说明与 plan 模式说明。

这对执行者是噪音，也把「岗位」「通道」「依赖」这些属于页面与编排层的概念暴露给了只会做一件事的执行者。同时，`description` 同时承担「页面给人看的说明」和「执行者看的指令」，两个读者抢同一段文字；要写清任务步骤，页面上的说明就变得又长又像 prompt。

任务创建也是同一个问题：`buka_task_create` 必须传 `channel`，而通道 id 只出现在上面那份可派发清单里——能力靠提示词喂，而不是靠工具发现。

## 决定

1. **定义升到 v6**：岗位与任务类型的 `description` 改名为 `prompt`，语义只有一个——执行这个节点 / 任务类型时注入给执行者的说明。工作流级的 `description` 保留，它只是列表摘要，不进执行提示词。
2. **执行提示词固定五段**，顺序不变：
   1. 工作流规则：引擎注入的能力说明（读资产、写资产、创建后续任务、提交结果）；
   2. 任务说明：岗位 `prompt`；
   3. 结果结构：任务类型 output schema 与 `buka_task_complete` 的提交方式；
   4. 任务类型说明：任务类型 `prompt`；
   5. 任务内容：模板渲染后的 payload。
3. **提示词不出现编排概念**：不写岗位 / 通道的 label 或 id、作业编号、依赖清单、附件清单、可派发清单，也不写「你在哪个岗位」。
4. **创建后续任务是工具能力，不是提示词清单**：
   - `buka_task_targets` 列出当前任务可创建的目标（任务类型 id、展示名、payload schema）；
   - `buka_task_create` 只接收 `target`、`payload` 与 `deps`，由引擎把目标解析成通道；同一目标对应多条通道时明确报错，要求作者消歧；
   - `buka_job_board` / `buka_task_get` 的工具输出裁掉岗位与通道字段。
5. **节点 / 任务类型 prompt 由作者写**：编排 preset 与 `buka_workflow_save` 的字段说明要求 prompt 只描述任务本身与完成后要做的事；需要创建后续任务时，在任务类型 prompt 里说明创建哪些目标。
6. **v5 → v6 一次性迁移**：岗位 / 任务类型 `description` 复制成 `prompt` 并删除 `description`；v4 定义先升级成 v5 再升到 v6；作业快照同迁。

## 后果

- 执行者拿到的上下文变短，只剩「规则 + 节点说明 + 结果结构 + 类型说明 + 内容」；上游结果通过 payload 模板进入内容，附件与产出走工具。
- 页面上岗位 / 任务类型的说明现在来自 `prompt`；任务抽屉不再显示任务类型说明。
- 同一对节点之间若有多条通道且白名单重叠，同一个目标会解析出多条路线，`buka_task_create` 会拒绝并要求作者拆开；需要精确路线的场景应把区别写进不同目标（任务类型）。
- 旧 v5 工作流的 description 会被原样迁成 prompt，其中可能仍写着通道 id 或旧工具参数；这些需要作者重写，迁移只保证不丢信息。
- 「通道是权限，不是管道」不变：通道仍由引擎校验与解析，只是不再出现在执行者的提示词与工具参数里。
