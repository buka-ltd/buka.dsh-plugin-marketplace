# ADR 0034：人任务提交即自动认领，页面不再单独认领

- 状态：已采纳（2026-11-24）；修订 ADR 0010 第 5 条的人任务交互
- 影响面：workflows 的任务详情投影（`allowedTaskActions`）、客户端任务抽屉、中英 i18n 与 DETAIL、README、GLOSSARY、测试；不改状态机、认领接口与存储

## 背景

ADR 0010 第 5 条定下「无助理时人直接处理」：任务停在 `ready`，人在看板认领、按动作表单填完提交。认领是独立按钮，人必须先点它把任务推到 `running`，表单里的提交按钮才可用。

这一跳不产生信息：提交本身已经会写认领者（`claimant = human`）、开始时间与一条执行记录；`completeHumanTaskLocked` 早就能从 `ready` 直接完成。页面上的强制认领只是把同一次状态转换拆成两次点击，还让「待你办理」的任务看起来要先「接单」。

## 决定

1. **页面不渲染「认领」按钮。** 就绪的人任务直接显示动作选择、动作表单与提交按钮。
2. **提交时自动认领。** 服务端沿用既有路径：`ready` 的人任务在完成前就地写认领者、开始时间与执行记录，再落结果与动作声明的创建；只提交结果与提交动作行为一致。
3. **保留认领流程。** `claimTaskAsHuman`、`/task/action` 的 `claim` 动作与任务详情 `allowedActions` 里的 `claim` 都保留，供其它客户端或将来显式的「接单」使用；只是页面不再把它当作必经步骤。
4. **用数据决定能否提交。** 就绪的人任务 `allowedActions` 同时给出 `claim` 与 `complete`；客户端按 `complete` 决定提交按钮是否可用，不再用状态自行推断。
5. **状态与看板列名不变。** `ready` 仍然表示「还没被接走」，认领改为随提交隐式发生；「待认领」列名留待单独的术语决定，本次不动。

## 备选与否决理由

- **删除认领接口与状态转换。** 认领仍要记录谁在何时接走任务，别的客户端也可能依赖；删除与「去掉一次点击」不是一回事。
- **提交前先发一次 claim 再发 complete。** 多一次往返，且两次请求之间失败会留下「已认领但没办」的悬挂任务；引擎已有的「从 ready 直接完成」路径更简单。
- **把「待认领」列改名为「待办理」或「就绪」。** 这牵动状态词表、看板列名与文档术语，和本次交互调整无关，不在同一个决定里做。

## 后果

- 人任务少一次点击；表单校验失败时任务仍是 `ready`，不会出现已认领却没办的中间态。
- 页面失去「先接单、稍后再办」的能力；需要显式接单的客户端仍可调用 `claim` 接口。
- 测试钉住三点：就绪人任务的 `allowedActions` 含 `complete`；任务抽屉没有认领按钮；提交只发一次 `complete` 请求。
