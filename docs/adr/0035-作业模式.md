# ADR 0035：作业是会话开头的一种模式，工作流由 agent 挑选

- 状态：已采纳（2026-11-25）；同日修订进入方式：命令不再要求 workflow id
- 影响面：workflows 的 `/job` 命令、`workflow_job_options` / `workflow_job_start` 的可见性与执行期校验、系统提示词（`workflow_job_policy`）、引擎新增 `jobModeTargets`、README / DETAIL / GLOSSARY、测试；不改存储、不改页面的人发起作业

## 背景

作业此前有三条会话侧入口：`/job <workflowId> <原始输入>` 命令、全局注册的 `workflow_job_start` 工具，以及页面的「新建作业」（人发起）。命令与工具都直接建单，因此：

- 任意会话的任意一轮都可以启动一个作业：模型可以在聊天中途调用 `workflow_job_start`，用户也可以在一段长对话里插一条 `/job`；
- `/job` 只有一条输入通道：把原始输入固定包成 `{ request }`，无法满足带结构化字段的开始节点 `content` schema；能填结构化输入的只有工具；
- 会话作为作业发起人的身份是隐式的：作业启动后最终报告会回到这个会话，但会话本身没有任何「我在办一个作业」的状态或指引。

计划模式（ADR 0032）已经证明了会话级模式的形态：一个由命令进入、折叠会话日志恢复、在系统提示词里注入段落的状态。作业需要的是同一类约束，但目的不是「先规划再执行」，而是「这个会话只负责启动一个作业」。

第一版实现让 `/job <workflowId>` 把目标钉在命令里，schema 随目标写进提示词。实际使用时发现问题：**让用户记 workflow id 本身是坏体验**；用户通常只会说想做什么，而不是先查 id。工作流应当由 agent 在会话里看一遍再选，选不出来时问用户。

## 决定

1. **`/job` 只能在会话开头进入作业模式，且不接收 workflow id。** 会话的第一条消息必须是 `/job [说明]`；日志里已经有 `user/message` 或 `turn/start` 时拒绝进入，并提示新建会话。说明可省略；非空时作为第一条用户消息投递（与 `/plan <message>` 同一机制）。`/job off` 退出。进入前只检查至少有一个已启用工作流；目标是否可用由列表工具如实报告。

2. **命令不再直接建单，也不解析目标。** 作业由模式内的 `workflow_job_start` 创建；目标由 agent 用 `workflow_job_options` 看到全部可启动工作流后选择或询问用户。这样既能按开始节点的 `content` schema 补齐结构化输入，也不要求用户记住标识符。

3. **作业模式注入两个工具，只在模式内可见。**
   - `workflow_job_options`：列出全部已启用工作流，带 id、名称、描述、开始节点输入 JSON Schema；定义版本过旧或引用的执行者缺失时也列出，并带不可用原因。
   - `workflow_job_start`：按选定的 id 与 `content` 建单；执行期再校验模式、是否已启动过作业、引擎里该会话是否已有作业。
   - 一个会话最多启动一个作业；启动成功即结束模式。

4. **系统提示词注入通用的 `workflow_job_policy` 段落，不内联具体工作流。** 顺序 520（紧跟计划模式之后），关闭变量插值；内容只写流程约束：先列工作流、按用户描述挑选、用户没说明用哪个或几个都像时先问、选定后按该工作流的 schema 补齐输入再启动、不启动就 `/job off`。

5. **作业模式的状态折叠自会话日志，不新增持久数据。** 三个信号：
   - `/job` 的 `command/run` → `command/done` 成功配对记录进入或退出；
   - `workflow_job_start` 的 `tool/call` → `tool/result`（`error` 缺省且 `message.isError` 不为 true）记录模式已消耗；
   - 日志里已有 `user/message` 或 `turn/start` 表示会话不再「刚开始」。

   恢复、fork 与压缩都从同一份日志还原；命令、提示词与两个工具的可见性读同一份折叠结果。正在执行的 `/job` 在提示词/工具那一档里先按已进入处理，因为 `agent.steer()` 会在命令结算前开启下一步。

6. **页面与重启路径不变。** 页面「新建作业」仍是人发起（`createJobFromHuman`），失败作业「从头新建」仍是人发起；作业模式只约束会话发起的作业。

## 备选与否决理由

- **保留 `/job <workflowId>`，只是不再全局建单。** 这正是第一版；用户仍要先去页面查 id，且说明文字与 id 挤在同一条命令里，无法区分「这是 id 还是描述」。所以第二版直接去掉 id。
- **把工作流列表写进系统提示词段落。** 列表和每个工作流的开始 schema 会在每个请求里重复；工作流变更后提示词直到重启才更新；而且用户想改选时没有刷新入口。工具调用一次、每次现查更合适。
- **只留一个 `workflow_job_start`，不带 id 时列清单。** 同一工具在「查询」和「变更」两种语义之间切换，模型容易误调；拆成列表与启动两个工具后，各自的说明与失败路径都清楚。
- **新增 Job 执行者预设，用模式选择器进入。** 预设是一组子插件，选它等于换掉整个会话的能力集；而这里要的只是「开头说清这个会话办作业」，预设反而把目标和输入契约挤到别处。用户也明确要求「以 job 开头」。
- **新增 `job/mode` 会话事件，照搬计划模式的投影。** 进入 / 消耗已经全部落在既有命令与工具事件上，再加一种事件只会多一份要与日志对齐的权威数据。
- **保留 `workflow_job_start` 全局可见，只靠提示词约束。** 这等于没有收窄：模型可以在任意会话里调用；而且用户要的正是「不要在任意位置嵌入作业」。

## 后果

- 普通会话不能再靠聊天启动作业；不支持斜杠命令的宿主失去会话侧入口，只能走页面。
- 启动一个作业需要先列一次工作流（一次工具往返）；换来的是用户不必知道 id，且 agent 能在多个工作流之间解释与询问。
- 目标不可用时列表仍会返回，由 agent 把原因转述给用户，而不是让命令在进入前失败。
- 模式状态没有新的存储格式；但日志折叠依赖 `command/run` / `command/done` 与 `tool/call` / `tool/result` 的形状，DSH 改这两类事件时需要同步。
- 测试钉住：日志折叠的进入 / 退出 / 消耗与失败不消耗、首条消息门禁、进入后补充说明、`/job off`、已启动后拒绝、无可用工作流拒绝、列工作流的引擎结果（含不可用原因）、`workflow_job_policy` 的注册与渲染、两个工具的可见性、真实 `commands` 服务的注册路径。
