# ADR 0004：兼容范围只写下限，不再封顶

- 状态：已采纳（2026-11-12）
- 影响面：`plugins/*/package.json` 的 `engines` 与 `peerDependencies`

## 背景

四个插件都写着 `"engines": { "dsh": ">=0.2.1-rc.5 <0.3.0" }`。查宿主的加载代码可以确认：
`dsh-app-boot` 在加载 profile 的 bundle 时会调用 `evaluatePluginCompatibility`，
不满足就直接抛错（`loadProfileDirectory` 里是 `throw`，不是跳过）；而且一旦声明了
`engines.dsh`，它**单独决定**是否兼容，`peerDependencies` 里的 `@deepseek-ai/dsh*` 范围被完全忽略。

也就是说：DSH 发布 0.3.0 的那天，所有已安装这些插件的用户会在启动时直接失败，
必须手工给每个「插件@版本」发一个精确版本豁免才能恢复。而官方 330 个包里**没有一个**
声明 `engines.dsh`。

## 决定

1. **只留下限：`"dsh": ">=0.2.1-rc.5"`。** 去掉 `<0.3.0`。
   下限是有用的（挡住缺 API 的旧宿主），上限只会自断后路——这个仓库没有理由赌 0.3.0 一定兼容，
   但更没理由在 0.3.0 发布时把用户挡在启动失败上。真要遇到不兼容，靠发新版修。

2. **`@deepseek-ai/cordis` 的 peer 范围对齐到 `~4.1.0`。** 宿主实际带的是 4.1.0，
   原来写的 `~4.0.5` 只是没被检查（加载器只检查 `@deepseek-ai/dsh*` 系列），不代表正确。

3. **`dsh.manifestVersion: 1` 保留**，但文档注明 DSH 不校验这个字段（官方 330 个包一个都没写它），
   它只是自我说明，不能当兼容性依据。

4. **不跟随官方"完全不写 `engines.dsh`"的做法。** 官方插件跟宿主一起发版，没有第三方
   装到旧宿主的问题；本仓库是独立发布的，需要一个下限。

## 后果

- 0.3.0 发布时插件仍能装、能启动；如果真有 API 不兼容，会在运行时表现为具体错误，
  而不是启动即失败。
- 以后再放宽/收紧兼容范围，改 `engines.dsh` 这一处即可（它单独决定，peer 范围只是文档）。
