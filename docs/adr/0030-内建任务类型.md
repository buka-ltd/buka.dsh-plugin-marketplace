# ADR 0030：开始 / 结束是内建任务类型，引擎是开始节点的处理人

- 状态：已采纳（2026-11-20）；取代 ADR 0008 决定 3、4 的执行语义
- 影响面：workflows 的定义校验、域类型、引擎、看板与页面、workers 的内建执行者、GLOSSARY、ADR 0008、插件 README 与 DETAIL、测试

## 背景

旧模型把开始 / 结束当成两个形状最小的内建节点：开始节点只有 `content` 与 `next`，结束节点只有 `content`，它们都不是任务类型。任务类型只属于岗位，于是同一个「任务契约」在两处用了两套说法：

- 开始节点的 `content` 实际上就是启动任务的任务内容 schema，`next` 实际上就是它的「完成后创建」；
- 结束节点的 `content` 实际上就是结束任务的任务内容 schema；
- 启动任务在建作业时被创建并立即完成，但节点本身没有处理人；结束任务的处理人又是发起人。

由此产生了一串特判：`resolveExecutor`、`resolveTargetTaskType`、看板把开始 / 结束合并成「发起人」行、任务抽屉对开始 / 结束隐藏处理人、定义抽屉把开始 / 结束画成契约而不是任务卡。节点、任务类型与任务实例三层混在了一起。

## 决定

1. **任务类型是纯契约，处理人属于节点。**
   任务类型只定义任务内容 schema、类型定义、动作、完成后创建等契约，不含处理人；处理人是节点的属性：岗位的处理人是作者声明的执行者，开始节点的处理人是引擎，结束节点的处理人是发起人（创建作业时可改成交付助理）。

2. **开始 / 结束是内建任务类型，每个工作流各声明一份。**
   - 开始任务类型：参数 schema（作业输入）+ 完成后创建（至少一条，线格式仍是 `start.next`）；
   - 结束任务类型：参数 schema（最终报告）；
   - `id`（`start` / `end`）、`label`、`definition` 固定，不可由作者写；
   - `actions`、`assistant`、`mode`、`worktree`（以及其它未声明字段）出现即定义错误；
   - 定义里只写这两个类型的可配置字段（`content`、`next`），身份与固定值由宿主提供。线格式保持 v8，不升版本。

3. **每个节点都有处理人 + 任务类型。**
   开始 / 结束仍是根级内建节点，各自承载一个内建任务类型，处理人档案固定：开始 = 引擎，结束 = 发起人 / 交付助理。作者不把它们写进 `positions`；节点的处理人不写进定义 JSON。

4. **引擎是内建执行者。**
   - 内建 worker：标识符 `engine`、展示名「引擎」、`driver: "robot"`、`program: "engine"`；
   - 在 Workers 页面只读展示并标「系统」，岗位不可选；定义校验拒绝岗位引用引擎；
   - 引擎程序由引擎自己执行（系统程序），不需要把 workflow id 等身份塞进任务参数；身份从 job / task 记录取得。

5. **建作业是引擎程序的一次执行。**
   `buka_job_start` 只暴露一个行为：用开始任务类型的参数创建作业。引擎程序接收创建请求（workflow、输入与交回方式），创建作业与启动任务，然后：
   - 按开始任务类型的参数 schema 校验输入；
   - 创建初始任务；
   - 把启动任务置为完成，或在校验 / 初始化失败时置为失败并把作业置为 `failed`。

   启动任务的 `assignee` 与 `claimant` 都是引擎。整个创建同步发生在 `buka_job_start` 的调用内，返回时作业已定型（成功或失败）。
   **入口处「一切皆任务」有一条例外：创建请求不是任务**；启动任务是引擎创建并完成的记录。

6. **失败留痕，不重试。**
   输入不合法或初始化失败时，保留 `failed` 作业与 `failed` 启动任务，`buka_job_start` 抛错并带上 job id。启动任务失败是终态：作业不提供从失败位置或从头开始的重启入口，页面引导用修正后的输入新建作业。

7. **看板按处理人分行。**
   引擎行（启动任务）、发起人行（结束任务）与岗位行并存，不再把开始 / 结束合并成一行。

8. **定义校验在保存时完成。**
   整份定义拒绝未知字段；`start` / `end` 必须显式声明；`start.next` 至少一条；两者的 `content` 保持可选；任务类型 id 与岗位 id 一样保留 `start` / `end`。

## 后果

- 开始 / 结束不再是「没有处理人的特殊节点」；节点、任务类型、任务实例三层各有明确职责，开始节点的输入就是启动任务的参数。
- 无效输入会留下一个 `failed` 作业，而不是只在调用方报错；作业历史更吵，但失败有据可查。
- 线格式保持 v8，已有工作流与 v7 / v8 作业快照继续可读；新增的严格校验会拒绝以前被静默剥离的未知字段，这类旧定义需要重写。
- Workers 页面多一个只读的系统执行者；岗位选择器与定义校验都要排除它。
- 看板多一行（引擎），任务抽屉与定义抽屉开始显示开始 / 结束节点的处理人。
- 启动任务 id 从全局保留的 `start-task` 改为 `start-task-<jobId>`：任务表按记录 id 做键，旧 id 会让后创建的作业覆盖前一个作业的启动任务；旧作业继续读 `start-task`，恢复逻辑改为按岗位找启动任务。
- 启动任务失败不能重启；重启入口需要按失败任务的位置区分，避免给出不可能成功的操作。
