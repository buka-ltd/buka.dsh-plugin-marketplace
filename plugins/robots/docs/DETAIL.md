# Buka Robots

Manage robots in the sidebar: independent subjects with a defined responsibility. There are two kinds: **agent robots** (a directory, AGENTS.md, project skills, and DSH sessions; created, registered and mounted as a workspace by this plugin) and **program robots** (a fixed program that takes input and produces output without a session; v1 ships only the built-in `clock`, read-only and not creatable/deletable). An agent robot marked `assistant: true` is an **assistant**: when a workflow human task names that assistant, only it may claim the task and talk to the person.

The page lists robot cards (avatar, name, driver, mount state, project skills, AGENTS.md, assistant, description). Agent robots can open a session, mount, rename, delete, install / remove project skills, edit AGENTS.md, set / unset assistant and change avatar; program robots are read-only. The list can filter to assistants only. Creating a robot makes its directory, writes an AGENTS.md template, registers it and mounts it as a workspace; the installed "robot builder" preset lets an agent clarify the responsibility and call `buka_robot_build` to create or rename a robot.

The registry `robots.json` is version 2: each robot adds `driver: "agent" | "program"` and `assistant`, and program robots add a `program` id. Reading a v1 registry fills `driver: "agent"` and `assistant: false`; the next write persists v2. Robot directories, AGENTS.md and skills are left untouched. `clock` is registered idempotently at startup and cannot be created, deleted, renamed or changed.

Other plugins use `ctx.bukaRobots`: `list()` returns summaries including driver / assistant / program, `avatarMap()` returns avatars, `dispatchSession()` always opens a new session, `openSession()` only resumes the same session, and handles expose `readResult` / `send` / `cancel` / `dispose` / `getPlanMode` / `setPlanMode`. One task gets one new session; compaction, blocking `startSession`, `outputSchema` / `routes` / `abortable`, and result retries are gone, and task results are submitted through the workflow's `buka_task_complete`. `planMode: true` runs `/plan` on the target agent before the first prompt.

A fresh install (empty registry) seeds two editable preset agent robots, "Software Engineer" and "QA Engineer". Avatar ids are a cross-plugin contract; project skills live under `<robot dir>/.agents/skills` and `.claude/skills`; AGENTS.md has a 256 KiB read limit and a 512 KiB save limit, and `CLAUDE.md` is kept as a relative symlink to it. Renaming moves the directory and recreates the DSH workspace; old session logs remain but no longer appear under that robot.
