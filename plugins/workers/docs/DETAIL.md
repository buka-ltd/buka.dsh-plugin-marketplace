# Buka Workers

Manage workers in the sidebar: independent subjects with a defined responsibility. There are two kinds: **agents** (a directory, AGENTS.md, project skills, and DSH sessions; created, registered and mounted as a workspace by this plugin) and **robots** (a fixed program that takes input and produces output without a session; v1 ships only the built-in `clock`, read-only and not creatable/deletable). An agent marked `assistant: true` is an **assistant**: when a workflow human task names that assistant, only it may claim the task and talk to the person.

The page lists worker cards (avatar, name, driver, mount state, project skills, assistant, description). Agents can open a session, mount, rename, delete, install / remove project skills, edit AGENTS.md, set / unset assistant, choose the model for new sessions and change avatar; robots are read-only. The list can filter to assistants only. Creating a worker makes its directory, writes an AGENTS.md template, registers it and mounts it as a workspace; the installed worker preset (display name "打工人", id `worker-builder`) lets an agent clarify the responsibility and call `buka_worker_build` to create or rename a worker.

The registry `workers.json` is version 3: each worker has `driver: "agent" | "robot"` and `assistant`, robots add a `program` id, and an agent may carry an optional `model` (`{ provider, model, reasoningEffort? }`). Reading a v1 registry fills `driver: "agent"` and `assistant: false`; a v2 `driver: "program"` is read as `"robot"`. The next write persists version 3. Worker directories, AGENTS.md and skills are left untouched. The model only affects sessions created afterwards in the worker directory (the page's New Session, a workspace opened from the sidebar, and workflow dispatch); existing sessions keep their own selection and can switch with `/model`. A saved selection survives while its model is temporarily missing from the catalog.

The package itself was renamed from `@buka/dsh-plugin-robots` to `@buka/dsh-plugin-workers`. On startup the default layout moves `~/.cache/dsh-plugin-robots` to `~/.cache/dsh-plugin-workers`, renames `robots/` / `robots.json` to `workers/` / `workers.json`, rebases the registered directory paths and upgrades the registry to version 3. For a custom `workersDir`: point it at the old directory (`.../robots`) and only the registry file is renamed and upgraded; point it at a sibling `.../workers` and both `robots/` and `robots.json` are renamed. The plugin does not guess any other old location. The old plugin remains a separate package: uninstall it after the new one is mounted. DSH workspace registrations that pointed at the old directories stop matching, so re-mount each worker from the page once after the migration; old session logs stay in the old workspace history.

Other plugins use `ctx.bukaWorkers`: `list()` returns summaries including driver / assistant / program, `avatarMap()` returns avatars, `dispatchSession()` always opens a new session, `openSession()` only resumes the same session, and handles expose `readResult` / `send` / `cancel` / `dispose` / `getPlanMode` / `setPlanMode`. One task gets one new session; compaction, blocking `startSession`, `outputSchema` / `routes` / `abortable`, and result retries are gone, and task results are submitted through the workflow's `buka_task_complete`. `planMode: true` runs `/plan` on the target agent before the first prompt.

A fresh install (empty registry) seeds two editable preset agents, "Software Engineer" and "QA Engineer". Avatar ids are a cross-plugin contract; project skills live under `<worker dir>/.agents/skills` and `.claude/skills`; AGENTS.md has a 256 KiB read limit and a 512 KiB save limit, and `CLAUDE.md` is kept as a relative symlink to it. Renaming moves the directory and recreates the DSH workspace; old session logs remain but no longer appear under that worker.
