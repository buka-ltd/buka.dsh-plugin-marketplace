# Buka Workers

Manage workers in the sidebar: independent subjects with a defined responsibility. There are two kinds: **agents** (a directory, AGENTS.md, project skills, and DSH sessions; created, registered and mounted as a workspace by this plugin) and **robots** (a fixed program that takes input and produces output without a session; v1 ships only the built-in `clock`, read-only and not creatable/deletable). An agent marked `assistant: true` is an **assistant**: when a workflow human task names that assistant, only it may claim the task and talk to the person.

Every worker has an immutable identifier (`id`) plus an optional display name (`name`). The identifier is the reference key used by workflows and the directory name (`workers/<id>`); it is chosen when the worker is created and can never be changed. The display name is only shown in the UI, need not be unique and can be changed at any time; when it is empty the identifier is shown. Lists, details and dialogs show both as "name · id" so same-named workers stay distinguishable.

The page lists worker cards (avatar, display name · id, driver, mount state, project skills, assistant, description). Agents can open a session, mount, rename (display name only), delete, install / remove project skills, edit AGENTS.md, set / unset assistant, choose the model for new sessions and change avatar; robots are read-only. The list can filter to assistants only. Creating a worker asks for a required identifier and an optional display name, makes the `workers/<id>` directory, writes an AGENTS.md template, registers it and mounts it as a workspace; the installed worker preset (display name "打工人", id `worker-builder`) lets an agent clarify the responsibility and call `buka_worker_build` with the approved id to create or update a worker.

The registry `workers.json` is version 4: each worker has an immutable `id`, an optional `name` (empty string means unset), `driver: "agent" | "robot"` and `assistant`; robots add a `program` id, and an agent may carry an optional `model` (`{ provider, model, reasoningEffort? }`). New identifiers match `^[a-z][a-z0-9_-]{0,63}$`. Reading a v1 / v2 / v3 registry migrates in memory: `id` becomes the old `name` and `name` becomes an empty string, so legacy identifiers (which may contain Chinese, uppercase or `.`) keep working for updates, renames and deletes; a v2 `driver: "program"` is read as `"robot"`, and v1 entries get `driver: "agent"` and `assistant: false`. The next write persists version 4. Worker directories, AGENTS.md and skills are left untouched. The model only affects sessions created afterwards in the worker directory (the page's New Session, a workspace opened from the sidebar, and workflow dispatch); existing sessions keep their own selection and can switch with `/model`. A saved selection survives while its model is temporarily missing from the catalog.

The package itself was renamed from `@buka/dsh-plugin-robots` to `@buka/dsh-plugin-workers`. On startup the default layout moves `~/.cache/dsh-plugin-robots` to `~/.cache/dsh-plugin-workers`, renames `robots/` / `robots.json` to `workers/` / `workers.json`, rebases the registered directory paths and upgrades the registry to version 4 (the migrated identifier is the old name, the display name starts empty). For a custom `workersDir`: point it at the old directory (`.../robots`) and only the registry file is renamed and upgraded; point it at a sibling `.../workers` and both `robots/` and `robots.json` are renamed. The plugin does not guess any other old location. The old plugin remains a separate package: uninstall it after the new one is mounted. DSH workspace registrations that pointed at the old directories stop matching, so re-mount each worker from the page once after the migration; old session logs stay in the old workspace history.

Other plugins use `ctx.bukaWorkers`: `list()` returns one summary per worker including its `id` and `name` (plus driver / assistant / program) so consumers can reference workers by identifier, `avatarMap()` maps identifiers to avatars, `dispatchSession()` always opens a new session, `openSession()` only resumes the same session, and handles expose `readResult` / `send` / `cancel` / `dispose` / `getPlanMode` / `setPlanMode`. One task gets one new session; compaction, blocking `startSession`, `outputSchema` / `routes` / `abortable`, and result retries are gone, and task results are submitted through the workflow's `buka_task_complete`. `planMode: true` runs `/plan` on the target agent before the first prompt.

A fresh install (empty registry) seeds two editable preset agents, `software-engineer` ("软件工程师") and `qa-engineer` ("质量保障工程师"). Avatar ids are a cross-plugin contract; project skills live under `<worker dir>/.agents/skills` and `.claude/skills`; AGENTS.md has a 256 KiB read limit and a 512 KiB save limit, and `CLAUDE.md` is kept as a relative symlink to it. Renaming only changes the display name: the directory does not move, the DSH workspace registration is kept (only its title is synced), and workflows that reference the identifier keep working.
