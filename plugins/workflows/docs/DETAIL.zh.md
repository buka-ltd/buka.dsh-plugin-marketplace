# Buka 工作流

持久工作流 + 作业看板。工作流是一张**岗位图**；作业 = 一个工作流版本 + 一份输入，每个作业一块看板；**任务**是最小工作单元，由执行中的任务随时产出，只能沿图上画出的通道派发。

## 模型

- **工作流**：持久定义，可多版本；由编排 preset 用 `buka_workflow_save` 保存，保存后即可使用；页面只负责审阅与停用 / 重新启用。定义只有当前版本（v7）有效，旧版本工作流标记「待升级」，不能再启动作业。
- **岗位**：图里的节点（内建开始 / 结束之外），给人看清流程结构。一个岗位一种执行者：人或打工人（agent / robot）；岗位只有名字和一段可选备注，不参与执行提示词。
- **任务类型**：岗位声明的任务契约：
  - **定义**（`definition`）：编排者预设的信息——这个任务类型是什么、要做什么、外部系统的事实（例如各服务的流水线地址），执行者都会读到；
  - **任务内容 schema**（`content`）：创建者为这一张任务填写的内容格式；
  - 人岗位的**动作**（`actions`）、可选助理、可选 plan 模式；
  - 机器人岗位的任务类型还必须声明 `content` schema，覆盖程序的内容契约（v1 的 clock 要求对象带必填 `until`）：保存工作流时检查声明，创建任务与执行前再按契约检查实际内容；
  - 机器人岗位的**完成后创建**（`creates`）：一组创建声明，机器人成功完成任务后由引擎沿通道创建；创建的任务依赖刚完成的任务，内容模板只认 `{{content.*}}`。这是「让 clock 等到点后继续干活」的写法。
- **任务内容**：创建者给这一张任务写的具体内容，可以是字符串，也可以是对象；引擎按任务类型的 content schema 校验，出错算创建者的错，在创建时就被拒绝。
- **动作**：人任务类型上的按钮。每个动作 = 名称 + 可选表单（input schema）+ 一组创建声明（沿哪条通道、建哪个任务类型、任务内容模板）。点击即派发的动作没有表单；一个动作可以创建多个任务，也可以一个都不建。
- **结果**：执行者交回的一段总结文本 + 附件。结果不进流程，只给管理作业的人看；流程价值在它创建的后继任务。
- **通道**：一条具名的派发路线，有 `id` 与人读的 `label`，从一个节点指向另一个节点；可带任务类型白名单；回向通道必须显式标注。同一对节点可以有多条通道，类型白名单可以重叠；任务记录自己走过的通道。通道是权限，不是管道：引擎不读 label。
- **开始 / 结束**：内建节点，执行者是发起人。开始节点的 `content` 是发起人填的作业输入，`next` 是提交后创建的初始任务；结束节点的 `content` 是最终报告，发起人确认收到后作业才结算。
- **交回方式**：创建作业时由发起人选择——交回发起人（会话发起投递进那个会话，人发起落在看板上），或交给一个助理代收。
- **作业**：一个工作流 + 一份输入，钉住工作流版本；编号在所属工作流内递增。不存在跨工作流的作业。
- **任务**：看板上的一张卡；有 pending / ready / running / completed / failed / blocked / cancelled 七种状态。除启动任务外，每个任务记录自己走过的通道。依赖纯显式，任务依赖图无环；每次打回产生新任务记录。
- **看板**：行 = 岗位（含开始 / 结束），列 = 排队 / 待认领 / 进行中 / 已完成 / 异常。

## 怎么用

1. 选「工作流编排」preset 新建会话，让编排 agent 起草岗位图，保存为工作流版本。
2. 在侧边栏「工作流」里审阅定义图与契约；暂时不用这个工作流时，在页头把它停用，需要时重新启用。
3. 新建作业：
   - 页面：填作业输入（开始节点的 content schema），选择最终报告交回自己还是交给助理，发起人 = 人；
   - 会话：用 `buka_job_start` 或 `/job` 命令给出作业输入，发起人 = 当前会话。
4. 作业看板上，打工人岗位自动认领就绪任务；人任务由点名的助理承办，或由人自己认领并点动作。跨分支看板可见整张作业；任务工具按数据流授权附件。
5. 执行中的任务沿通道创建后续任务；最后交出结束任务，发起人确认收到，作业结算。

## 工具

| 工具 / 命令                                | 作用                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------- |
| `/job`                                     | 普通会话入口：列可用工作流，或按输入启动一个作业（发起人 = 当前会话） |
| `buka_workflow_save`                       | 编排 preset 根会话：校验并保存工作流新版本（保存后即可用）            |
| `buka_workflow_list` / `buka_workflow_get` | 读工作流目录 / 全文                                                   |
| `buka_job_start`                           | 会话里启动作业：给作业输入与交回方式                                  |
| `buka_job_status` / `buka_job_cancel`      | 读作业、取消作业                                                      |
| `buka_task_targets`                        | 执行中的任务：列出当前可创建的任务目标与任务内容 schema               |
| `buka_task_create`                         | 执行中的任务：按目标随时创建下游任务（可多次），通道由引擎解析        |
| `buka_task_actions`                        | 执行中的任务：列出人任务可点的动作与动作表单 schema                   |
| `buka_task_complete`                       | 执行中的任务 / 助理：提交结果文本与附件；人任务可带动作与表单         |
| `buka_job_board` / `buka_task_get`         | 执行中的任务 / 助理：只读作业看板、任务与依赖                         |
| `buka_job_attachments`                     | 执行中的任务 / 助理：按可见范围检索 / 读取附件                        |

编辑工作流的工具只对 `orchestratorPresets` 点名的 preset 根会话、以及 `orchestratorWorkspaces` 点名目录里的会话可见；执行工具只对本次任务会话、助理会话与发起人会话可见。人任务没有模型回答工具。

## 执行提示词

执行者（agent 任务、助理）只看到三段，顺序固定：

1. **工作流规则**：引擎注入的能力说明——读写资产、`buka_task_targets` / `buka_task_create` 创建后续任务、`buka_task_complete` 提交结果；
2. **任务类型的定义**：任务类型的 `definition`，预设信息都在这里；
3. **任务内容**：创建者给这一张任务的内容（字符串原样，对象按 JSON）。

岗位名、通道 id、作业编号、依赖清单与附件清单都不进提示词——这些是页面与编排层的信息，避免把「岗位 / 通道」这类构建工作流的概念暴露给执行者。任务内容里的模板只在定义声明的创建（人任务动作、开始节点 `next`）里求值，可用 `{{content.<path>}}`（正在完成的任务内容）与 `{{input.<path>}}`（动作表单）。

## 人任务与助理

- 人任务 = 人岗位产出的普通任务，没有「等待人工」状态，所有任务都在看板上。
- 人任务类型可以点名一个 `assistant`（智能体的名字）或 `null`：
  - 点名助理：任务就绪后引擎启动该助理的会话；助理拿到整张任务卡片（任务内容、动作与表单），负责与人沟通，然后代人点动作完成。
  - `null`：任务停在待认领，人在看板认领、点一个动作（有表单的填完）提交，或者只提交结果不创建任务。
- 助理失败后任务回到待认领，不自动换助理；人始终可以兜底完成。

## 结束任务与交回

- 结束任务由前一个任务沿通道创建，`content` 就是最终报告，按结束节点的 content schema 校验。
- 交回方式在创建作业时定：
  - **交回发起人**：会话发起时，最终报告投递进那个会话，等会话调 `buka_task_complete` 确认；人发起时，结束任务落在发起人自己的看板上，由他点「已收到」。
  - **交给助理**：结束任务的执行者是指定的助理，由它代收并确认。
- 发起人确认后作业才变成 completed；投递失败可以重试。

## 附件

每个作业一个附件库。附件必须记录来源任务 / 岗位、创建者、大小、mime、sha256 与描述；可见性按数据流：产出任务、传递依赖它的任务、发起人与作业页面。不相关分支不能列出、检索或读取。文件存插件作业目录，元数据进 `ctx.storageDomain`。

## 页面

侧边栏「工作流」只有一条链：**工作流列表 → 工作流 → 作业**。

- **工作流列表**：名称、版本、作业数；停用的工作流留在列表里，灰显并排在后面；旧版本定义的工作流带「待升级」标签。
- **工作流页**分两个页签：
  - **作业**（默认）：按全部 / 进行中 / 已完成 / 异常筛选；作业卡片显示输入摘要、任务进度与待认领数；旧版本定义的作业带「旧版本」标签且不能点开。
  - **结构图**：可交互的分层图，从上到下排布，图例固定在画布底部。点岗位节点看执行者、维护备注与可处理的任务类型，点开始 / 结束节点看 content 契约，点通道看发送方、接收方与允许的任务类型。
- **作业页**分四个页签：
  - **概览**（默认）：作业输入、最终报告、启动信息与错误。
  - **实时流程**：同一张定义图上叠加任务状态——谁在做什么、完成 / 总数、待认领与异常；点节点打开该岗位的任务。
  - **看板**：行 = 岗位，列 = 排队 / 待认领 / 进行中 / 已完成 / 异常；窄屏退化成按状态分组的列表。
  - **资产**：资产池，按来源任务分组；最终报告同时标在概览里。
- **任务抽屉**：先看结果与可执行的操作，再看任务内容、依赖与附件。人任务先选动作，再填这个动作的表单；执行记录、类型与时间收进默认折叠的「更多信息」；结束交付失败时提供「重试交付」。

## 依赖与存储

- 需要 `@buka/dsh-plugin-workers` 提供打工人登记与任务会话；需要 DSH 组合里的 `ctx.storageDomain`（base 组合自带）。
- 工作流 / 作业 / 任务 / 执行记录 / 附件元数据在 `ctx.storageDomain` 的 `buka_workflow` 域；大文本与附件文件在插件数据目录 `~/.cache/dsh-plugin-workflows/jobs/<jobId>/`。
- **版本策略**：定义格式只有当前版本（v7）有效，打开存储时不做任何转换。旧版本定义的工作流保留在列表里，带「待升级」标签，不能再启动作业；升级 = 由编排者在当前格式下重写一份新版本。旧版本定义的作业同样只读、不能打开。

## 配置

配置项以 `src/options.ts` 为准：工作流数据目录、编排 preset 名单、按工作区放行的目录、打工人 preset、任务并发与预算等。默认 `orchestratorPresets` 是随包发布的 `workflow-orchestrator`；`orchestratorWorkspaces` 默认为空，填了以后这些目录（含子目录）里的会话不用切 preset 也能保存 / 读取定义，适合插件自己的开发者工作区。

## 结构

- `src/domain/**`：类型、状态机、id。
- `src/store/**`：storageDomain 表、per-job 串行队列、作业目录。
- `src/definition/**`：工作流 v7 校验与任务内容模板。
- `src/engine/**`：调度、执行器、结算、恢复。
- `src/tools/**`、`src/commands/**`：模型工具与 `/job` 命令。
- `src/routes/**`：页面只读 / 操作路由。
- `src/client/**`：侧边栏页面。
- `lib/index.js`、`lib/client.js`：构建产物，提交进 git，不手改。
