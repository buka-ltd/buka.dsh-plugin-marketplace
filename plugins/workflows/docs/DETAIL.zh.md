# Buka 执行者与工作流

有明确职责的**执行者** + 持久工作流 + 作业看板，一个插件装下整条「把团队关进公司」的流水线：技能给能力，执行者担职责，工作流约束结构，看板把任务分发到岗位，并在关键节点停下来等人。

## 执行者

执行者分两类：**智能体**（有目录、AGENTS.md、项目 skills，以 DSH 会话执行任务；由插件创建、登记并挂载成工作区）与 **机器人**（固定程序，接收输入 → 产出输出，不建会话；v1 只有内建的 `clock`，只读、不可创建 / 删除）。助理不是执行者身上的标记：工作流在人任务类型或交回方式上点名一个智能体，被点名的智能体才代办那张任务或代收最终报告。

- 每个执行者都有不可变标识符（`id`）与可选展示名（`name`）。标识符是工作流的引用键、也是目录名（`workers/<id>`）：创建时指定、之后不可修改；名称只用于展示，可随时改、不要求唯一，为空时显示标识符。
- 页面列出执行者卡片（头像、名称 · id、driver、挂载状态、项目 skills、职责）。智能体可新开会话、挂载、删除、安装 / 移除项目 skills、在「设置」页签改展示名、职责与新会话模型（改动即自动保存）、在只读的「文件」页签浏览执行者目录与代码内容、换头像；机器人只读。
- 删除是**硬删**：登记条目、执行者目录与工作区注册行一起删除，没有归档状态。确认弹窗先展示影响面——引用该标识符的**运行中作业**（唯一删除阻塞）、会因此变成「不可用」的工作流、引用它的已结束作业数与将被删除的目录——并写明目录里的 AGENTS.md 与项目 skills 会一起消失；不提供强制删除。
- 登记表 `workers.json` 为 version 4：每条有不可变 `id`、可选 `name` 与 `driver: "agent" | "robot"`，机器人另有 `program` id，智能体可带可选的 `model`。新标识符匹配 `^[a-z][a-z0-9_-]{0,63}$`；读旧版本表时在内存里迁移，旧标识符仍可用于更新、改名与删除。
- 全新安装（登记表为空）时补两个可编辑的预设智能体：`software-engineer`（软件工程师）与 `qa-engineer`（质量保障工程师）。
- 项目 skills 落在 `<执行者目录>/.agents/skills` 与 `.claude/skills`；AGENTS.md 读取上限 256 KiB、保存上限 512 KiB，`CLAUDE.md` 自动做成指向它的相对符号链接。
- 执行者目录默认初始化为独立 git 仓库：创建执行者时 `git init`，已有目录在列表加载时补齐；**不自动提交**，首个提交由用户自己决定。接上远端后即可推送 / 分享。目录已位于另一个仓库里时不建嵌套仓库；本机没有 git 或初始化失败只降级，不影响执行者的创建与使用。

历史：插件曾叫 `@buka/dsh-plugin-robots`（后改名 workers），启动时会把旧缓存目录与登记表自动迁移到 `~/.cache/dsh-plugin-workers/`。2026 年 11 月起 workers 与 workflows 合并为同一个包（见文末「升级与迁移」）。

## 工作流模型

- **工作流**：持久定义，可多版本；由编排预设用 `buka_workflow_save` 保存，保存后即可使用；页面只负责审阅与停用 / 重新启用。定义只有当前版本（v8）有效；v7 定义在打开存储时自动迁移到 v8，其它版本的工作流标记「待升级」，不能再启动作业。
- **岗位**：图里的节点（内建开始 / 结束之外），给人看清流程结构。一个岗位一种主体：工作人员或执行者（agent / robot），执行者按不可变标识符引用；岗位只有名字和一段可选备注，不参与执行提示词。
- **任务类型**：岗位声明的任务契约：
  - **定义**（`definition`）：编排者预设的信息——这个任务类型是什么、要做什么、外部系统的事实（例如各服务的流水线地址），执行者都会读到；
  - **任务内容 schema**（`content`）：创建者为这一张任务填写的内容格式；
  - 人岗位的**动作**（`actions`）、可选助理（点名执行者标识符）、可选 plan 模式；
  - 智能体岗位可选的**工作树模式**（`worktree`）：`none`（不注入任何工作树提示词，省略等同于此）、`guard`（不创建工作树，只要求执行者检查当前工作区与任务要修改的每个仓库是否干净，有未提交修改就停下来问用户）、`create`（要求执行者自己按仓库调用 `create_worktree`，任务可能同时改多个仓库，从各自的仓库目录创建）。`create` 需要宿主同时提供工作树服务（`ctx.worktrees`）与 `create_worktree` 工具，缺失时自动降级为 `guard`；
  - 机器人岗位的任务类型还必须声明 `content` schema，覆盖程序的内容契约（v1 的 clock 要求对象带必填 `until`）：保存工作流时检查声明，创建任务与执行前再按契约检查实际内容；
  - 机器人岗位的**完成后创建**（`creates`）：一组创建声明，机器人成功完成任务后由引擎沿通道创建；创建的任务依赖刚完成的任务，内容模板只认 `{{content.*}}`。这是「让 clock 等到点后继续干活」的写法。
- **任务内容**：创建者给这一张任务写的具体内容，可以是字符串，也可以是对象；引擎按任务类型的 content schema 校验，出错算创建者的错，在创建时就被拒绝。
- **动作**：人任务类型上的按钮。每个动作 = 名称 + 可选表单（input schema）+ 一组创建声明（沿哪条通道、建哪个任务类型、任务内容模板）。点击即派发的动作没有表单；一个动作可以创建多个任务，也可以一个都不建。
- **结果**：主体交回的一段总结文本 + 附件。结果不进流程，只给管理作业的人看；流程价值在它创建的后继任务。
- **通道**：一条具名的派发路线，有 `id` 与人读的 `label`，从一个节点指向另一个节点；可带任务类型白名单；回向通道必须显式标注。同一对节点可以有多条通道，类型白名单可以重叠；任务记录自己走过的通道。通道是权限，不是管道：引擎不读 label。
- **开始 / 结束**：内建节点，主体是发起人。开始节点的 `content` 是发起人填的作业输入，`next` 是提交后创建的初始任务；结束节点的 `content` 是最终报告，发起人确认收到后作业才结算。
- **交回方式**：创建作业时由发起人选择——交回发起人（会话发起投递进那个会话，人发起落在看板上），或交给一个助理（点名执行者标识符）代收。
- **作业**：一个工作流 + 一份输入，钉住工作流版本；编号在所属工作流内递增。不存在跨工作流的作业。
- **重启**：失败作业的两种继续方式——从失败位置在同一个作业里恢复，或按原作业输入从头新建一个作业。
- **任务**：看板上的一张卡；有 pending / ready / running / completed / failed / blocked / cancelled 七种状态。除启动任务外，每个任务记录自己走过的通道。依赖纯显式，任务依赖图无环；每次打回产生新任务记录。
- **看板**：行 = 岗位（含开始 / 结束），列 = 排队 / 待认领 / 进行中 / 已完成 / 异常。

## 怎么用

1. 选唯一的 **Workflow** 预设新建会话，让编排 agent 起草岗位图、保存为工作流版本；同一个会话也可以让它创建 / 修改执行者（先展示草案、等你批准）。
2. 在侧边栏唯一的入口里管理：**Workflow** 页签审阅定义图与契约，暂时不用时在页头把工作流停用，需要时重新启用；**Worker** 页签管理职责与项目 skills。
3. 新建作业：
   - 页面：填作业输入（开始节点的 content schema），选择最终报告交回自己还是交给助理，发起人 = 人；
   - 会话：用 `buka_job_start` 或 `/job` 命令给出作业输入，发起人 = 当前会话。
4. 作业看板上，执行者岗位自动认领就绪任务；人任务由点名的助理承办，或由人自己认领并点动作。跨分支看板可见整张作业；任务工具按数据流授权附件。
5. 执行中的任务沿通道创建后续任务；最后交出结束任务，发起人确认收到，作业结算。

## 执行提示词

执行者（agent 任务、助理）看到的提示词按固定顺序拼装：

1. **工作流规则**：引擎注入的能力说明——读写资产、`buka_task_targets` / `buka_task_create` 创建后续任务、`buka_task_complete` 提交结果；
2. **工作树规则**（仅任务类型的 `worktree` 不是 `none` 时出现）：`create` 生效时要求执行者按仓库自己调用 `create_worktree`，多仓库分别创建、用 `working_directory` 切换；`guard`（显式选择，或 `create` 降级）只说明不创建新工作树，要求执行者先检查工作区与要修改的每个仓库、有未提交修改就必须停下来询问用户；
3. **任务类型的定义**：任务类型的 `definition`，预设信息都在这里；
4. **任务内容**：创建者给这一张任务的内容（字符串原样，对象按 JSON）。

岗位名、通道 id、作业编号、依赖清单与附件清单都不进提示词——这些是页面与编排层的信息，避免把「岗位 / 通道」这类构建工作流的概念暴露给执行者。任务内容里的模板只在定义声明的创建（人任务动作、开始节点 `next`）里求值，可用 `{{content.<path>}}`（正在完成的任务内容）与 `{{input.<path>}}`（动作表单）。

## 人任务与助理

- 人任务 = 人岗位产出的普通任务，没有「等待人工」状态，所有任务都在看板上。
- 助理是**工作流上的点名**，不是执行者身上的标记：人任务类型用 `assistant` 点名一个智能体（或 `null`），交回方式也可以点名一个智能体代收最终报告。校验只要求标识符已登记且 `driver: "agent"`；任何已登记的智能体都能被点名，不需要先被「标记为助理」。
- 人任务类型点名一个 `assistant`（智能体标识符）或 `null`：
  - 点名助理：任务就绪后引擎按标识符启动该助理的会话；助理拿到整张任务卡片（任务内容、动作与表单），负责与人沟通，然后代人点动作完成。
  - `null`：任务停在待认领，人在看板认领、点一个动作（有表单的填完）提交，或者只提交结果不创建任务。
- 被点名的助理没交出结果时（会话结束未提交、超时、恢复失败），任务标失败、作业立即失败：其余非终态任务被取消并写清终止原因，作业错误写明是哪条任务、哪个代办者、什么原因。不自动换助理，人也不能接手。

## 重启失败作业

失败的作业不是死路：只有 `failed` 的作业显示「重启作业」入口，`completed` 与 `cancelled` 没有入口。弹窗给两个选项，可用性与不可用原因由服务端判定，客户端只按它渲染。

- **从失败位置**：同一个作业就地恢复，作业 `failed → running`。失败的任务回到 `ready`，重新派给原主体并追加一条新的执行记录；因作业终止被取消的任务回到 `pending`，按依赖重新就绪；被阻塞的任务在其依赖不再失败 / 阻塞 / 人主动取消后回到 `pending`。人主动取消的任务保持取消，已完成的任务连同结果与执行记录不动。作业记录重启次数，最长时长预算的计时起点重置为重启时刻。
- **从头开始**：按原作业输入、用工作流**当前启用的版本**新建一个作业；发起人是点重启的人，交回方式沿用原作业（原本交回发起人的改为交回新发起人）。新作业记录来源作业 id，原失败作业留在 `failed` 作为现场，仍可查看。工作流已停用或不在当前定义版本时这个选项不可用。
- 没有失败任务的失败作业（例如分支全被取消、结束任务交付失败）只提供「从头开始」。
- 重启是人的显式动作，不是自动重试：代办再次失败仍然直接失败作业，可以再次重启。重启用的是同一个作业钉住的定义版本；从头开始才按改过的流程重来，两个作业各自有预算与看板、互不影响。
- 状态机补了三条规定：作业 `failed → running`；任务 `blocked → pending` 与引擎取消的 `cancelled → pending`。这两条任务转换只由引擎在重启时使用；人主动取消的任务在终止时不写错误信息，重启时靠它区分，不复活。

## 不可用（派生状态）

工作流与作业可能进入派生的「不可用」：它们引用的执行者标识符在登记表里查不到了。不可用不落盘，由读取方按引用能否解析实时计算；重新绑定一个已存在的执行者后自动恢复。

- **引用来源**：工作流任一版本的岗位主体、任务类型助理；作业钉住的定义（岗位主体、任务类型助理）与交回方式的助理。v7 作业快照里的旧 `name` 值也按标识符解析。
- **工作流**：列表与详情标出缺哪个标识符，不能启动作业；保存新定义时仍会校验标识符存在（读取既有定义不校验，只标不可用）。
- **作业**：作业页标注「不可用」；缺失执行者的任务派发失败，错误里写明是哪条任务、哪个岗位、缺哪个标识符，任务可重试，其它分支继续跑。点名的助理已不存在的人任务不再自动派发，留在「待认领」由人兜底完成。
- **与「停用」的区别**：停用是人为收起，已有作业照常运行；不可用是引用断了，需要重新绑定。历史展示里已删执行者的岗位 / 任务 / 点名的助理显示占位头像与「已删除」，不保留墓碑记录。

删除执行者是硬删（登记条目、目录与工作区注册一起删除），唯一阻塞是引用该标识符的运行中作业。删除确认弹窗通过本插件内的只读服务 `ctx.bukaWorkflows.workerUsage(id)` 取得引用面。

## 结束任务与交回

- 结束任务由前一个任务沿通道创建，`content` 就是最终报告，按结束节点的 content schema 校验。
- 交回方式在创建作业时定：
  - **交回发起人**：会话发起时，最终报告投递进那个会话，等会话调 `buka_task_complete` 确认；人发起时，结束任务落在发起人自己的看板上，由他点「已收到」。
  - **交给助理**：结束任务的主体是指定的助理，由它代收并确认。
- 发起人确认后作业才变成 completed；投递失败可以重试。

## 附件

每个作业一个附件库。附件必须记录来源任务 / 岗位、创建者、大小、mime、sha256 与描述；可见性按数据流：产出任务、传递依赖它的任务、发起人与作业页面。不相关分支不能列出、检索或读取。文件存插件作业目录，元数据进 `ctx.storageDomain`。

## 页面

侧边栏只有一个入口，首页顶部两个页签，第一个 **Workflow**、第二个 **Worker**。页签由 hash 驱动：`#/workers`（或 `#/workers/…`）落在 Worker 页签，其余 hash 都是工作流路由；刷新、前进 / 后退都保持页签，切回 Workflow 页签时恢复上一次的工作流 hash（如作业页）。

首页页签只出现在两个列表页。进入工作流详情、作业详情或执行者详情后，页头换成独立设计：第一行是返回 + 标题 + 状态 / 操作，第二行是页内页签（作业 / 结构图、概览 / 实时流程 / 看板 / 资产、设置 / 文件 / 技能），不再在顶部压一层首页页签。

- **Workflow**：一条链——**工作流列表 → 工作流 → 作业**：
  - **工作流列表**：名称、版本、作业数；停用的工作流灰显排在后面；旧版本定义的工作流带「待升级」标签。
  - **工作流页**：**作业**（默认，按状态筛选；v7 快照的作业带「旧版本」标签但仍可打开、继续推进）与**结构图**（可交互的分层图，点岗位看主体与任务类型，点开始 / 结束看 content 契约，点通道看收发方与允许类型）。
  - **作业页**：**概览**（输入、最终报告、启动信息与错误）、**实时流程**（任务状态叠在定义图上；有会话等你操作或回复时，节点左上角显示小红点）、**看板**（岗位 × 状态；窄屏退化成按状态分组的列表）、**资产**（按来源任务分组）。
  - **任务抽屉**：先看结果与可执行的操作，再看任务内容、依赖与附件。人任务先选动作再填表单；结束交付失败时提供「重试交付」。
  - **重启作业**：失败的作业在作业页顶部显示入口，按服务端可用性置灰并显示原因；从头开始的新作业可以跳到原作业。
- **Worker**：列表视图按 `driver` 展示驱动标签（agent / robot），整行点击进详情；详情按页签分成「设置」「文件」「技能」；「设置」里放名称、职责与模型，都没有保存按钮——停止输入 / 选完即自动保存；「技能」页签在进入详情页时自动探测更新（页签上显示更新圆点），有更新的 skill 在行内单独更新，安装入口在执行者页头右上角（「刷新」右侧），点击后只列 Skills 插件「技能仓库」里收藏的来源——未收藏的第三方仓库要先在 Skills 页面收藏，执行者弹窗不再接受手填来源；页头的「打开」是分体按钮：主按钮用上次选定的应用打开执行者目录，箭头可从 DSH 内置 open-in-app 探测到的应用里换一个（选择与 DSH 其它入口共享），清单不可用时退回系统文件管理器；「文件」页签左侧是执行者目录树、右侧只读展示所选文件内容，不提供编辑 / 保存。机器人（内建 clock）只读：没有新会话 / 挂载 / 删除入口，也不能浏览文件或安装 skills。删除弹窗在确认前展示影响面（见「执行者」一节）。

两个页签互相跳转：删除执行者的影响面弹窗里「打开作业」只写 `#/job/...`，首页自动切回 Workflow 页签并打开对应作业。切页签只挂载活动页：执行者页的选中态 / 草稿不跨页签保留（与合并前两个面板互切的行为一致）。

## 依赖与存储

- 执行者登记与任务会话由本插件自带（`ctx.bukaWorkers` 服务）；工作流元数据需要 DSH 组合里的 `ctx.storageDomain`（base 组合自带）。
- **工作树能力是可选的**：任务类型的 `worktree: "create"` 依赖 DSH 的工作树插件（`ctx.worktrees` 与 `create_worktree` 工具，通常由「变更请求与工作树」组合包提供）。插件未启用时定义照常保存，执行时降级为 `"guard"`；`"none"` 与 `"guard"` 不依赖任何工作树能力。插件不预先创建检出，由执行者按任务自己调用工具。
- 执行者数据在 `~/.cache/dsh-plugin-workers/`（`workers.json` 登记表 + `workers/<id>/` 目录）；工作流 / 作业 / 任务 / 执行记录 / 附件元数据在 `ctx.storageDomain` 的 `buka_workflow` 域；大文本与附件文件在插件数据目录 `~/.cache/dsh-plugin-workflows/jobs/<jobId>/`。
- **版本策略**：定义格式当前版本是 v8。打开存储时会把 v7 工作流定义迁移到 v8（主体的 `name` 字段改名为 `id`，值不变），迁移幂等。其它版本的工作流保留在列表里，带「待升级」标签，不能再启动作业；升级 = 由编排者在当前格式下重写一份新版本。作业快照不迁移：v7 作业保留旧 `name` 字段，仍可读取、恢复与推进。

## 配置

配置项以 `src/options.ts`（工作流）与 `src/workers/index.ts`（执行者）为准：执行者根目录（`workersDir`）、写工具可见的 preset 名单（`builderPresets`）、预设执行者种子（`seedPresets`）、工作流数据目录、编排 preset 名单、按工作区放行的目录、执行者会话 preset、任务并发与预算等。默认 `builderPresets` 与 `orchestratorPresets` 都是随包发布的 `workflow-orchestrator`（显示名 `Workflow`）；`orchestratorWorkspaces` 默认为空，填了以后这些目录（含子目录）里的会话不用切 preset 也能保存 / 读取定义，适合插件自己的开发者工作区。

## 升级与迁移

本插件由 `@buka/dsh-plugin-workers` 与 `@buka/dsh-plugin-workflows` 两个插件合并而成（版本 4.0.0）：

1. **先卸载旧的两个插件，再安装本插件**。新旧并存会重复注册同名服务 / 工具 / 补丁行（`preset-workflow-orchestrator` 等），导致组合冲突。
2. **数据零迁移**：执行者目录与登记表、工作流定义、作业看板都在原来的位置，合并后原样读取。
3. **预设合并**：旧的「执行者」（`worker-builder`）与「工作流编排」（`workflow-orchestrator`）两个预设合并为唯一的 **Workflow** 预设（id 沿用 `workflow-orchestrator`），既能设计 / 保存工作流，也能创建 / 修改执行者。旧预设的历史会话仍可继续。
4. 插件配置按 DSH 的保存机制重置为默认；默认目录与旧版一致，之前自定义过 `workersDir` / `dataDir` / 预设名单的，在设置里重新填一次即可。

## 结构

- `src/workers/**`：执行者一半——登记表、目录、AGENTS.md、项目 skills、模型工具与 `/buka-workers/*` 路由。
- `src/domain/**`、`src/store/**`、`src/definition/**`、`src/engine/**`：工作流类型、状态机、存储域、定义校验与调度引擎。
- `src/tools/**`、`src/commands/**`：工作流模型工具与 `/job` 命令。
- `src/routes/**`：工作流页面路由。
- `src/client/**`：工作流页面；`src/client/workers/**`：执行者页面；`src/client/home.ts` 装配首页的两个页签。
- `src/index.ts`、`src/client/index.ts`：合并后的两个装配入口（只装配）。
- `lib/index.js`、`lib/client.js`：构建产物，提交进 git，不手改。
