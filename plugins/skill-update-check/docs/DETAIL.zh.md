# SKILL 更新提示

在当前工作区检查项目技能是否有上游更新：有更新时，在新建会话输入框的
**下方**、统计行最右侧（「上下文已用」圆环之后）显示一个 warn 色提示。
点击提示弹出「SKILL 更新」弹窗：列出过期的项目技能，每一行一个「更新」，
页脚一个「全部更新」。

检查与更新都走 `skills` 包自带的 CLI —— 也就是 `npx skills` 背后的同一套
实现 —— 读取工作区根目录的 `skills-lock.json`：检查跑 `check -p`，更新跑
`update <name> -p`。插件把 `skills` 声明为运行时依赖，安装插件时会一起装好；
不需要另外安装 Skills 插件。

## 出现位置

提示注册在插槽 `conversation.composer.dock`：输入框卡片下方的统计行。
统计行的 `activity` / `usage` 两个条目由插槽渲染，「上下文已用」圆环由输入框
自己追加在插槽之后；提示用 flex 的 `order` 排在所有默认项之后，也就是圆环
右侧。圆环不显示时（上下文用量还不可用，或工具栏被活动控件占用），提示仍然
落在统计行最右端。它只在有项目技能更新时出现：

- 中文界面：`3 个技能可更新`
- 英文界面：`3 skill updates`

颜色取 DSH 主题的 `--dsw-alias-state-warn-primary`；背景是同色系的浅
tint，跟随浅色 / 深色主题。悬停显示前 5 个 skill 名与「点击查看并更新」。

弹窗里每一行是技能名 + 它在 `skills-lock.json` 里记录的来源仓库（例如
`mattpocock/skills`），方便确认这次更新的是哪个来源；没有来源记录时只显示
名字。弹窗不重复工作区路径，也不加一段泛泛的说明文案。

没有更新、工作区没有项目技能、或首次检查还没跑完时，这个位置保持原来的
布局，不占宽度。检查失败时提示缩成一个 `!`（error 色），tooltip 显示原因，
点击也会打开弹窗，弹窗里可以重新检查。

## 检查流程

1. 浏览器只把当前会话 id 发给 Host；不传路径，也不读文件系统。
2. Host 解析当前工作区：
   - 优先在 `workspaceRegistry` 里找 `sessionIds` 包含该会话的工作区；
   - 找不到时取会话 header 的 `cwd`，再在已注册工作区里找包含它的最长
     路径（会话在子目录里时仍检查工作区根目录）；
   - 两者都没有时返回 `unavailable`，不显示提示。
3. 读 `<工作区>/skills-lock.json`。文件不存在说明这个工作区没有由
   `npx skills` 管理的项目技能，直接结束，不启动 CLI。
4. 用插件依赖里的 `skills` CLI 执行 `check -p -y`，工作目录是工作区根目录。
   退出码 0 与 1 都是正常结论：1 表示有更新或有本地修改；其它退出码、
   超时或进程没启动起来才算检查失败。
5. 解析输出里的 `↑ <name> has an update` 与 `✎ <name> has local changes`。
   **有本地修改的 skill 不算可更新**：即使上游也有更新也不进列表，只在弹窗里
   注明「有本地修改，未参与更新」，避免更新覆盖你的改动。

同一个工作区在 5 分钟内只跑一次 CLI；多个会话同时挂载时共用同一个进行
中的 Promise。打开弹窗直接复用提示已经拿到的快照，结果超过 5 分钟才在后台
补一次检查，旧列表保持可见；只有点「重新检查」才传 `refresh=1` 跳过缓存。
检查是只读的：不写 lockfile，不安装、不更新任何 skill。

## 更新流程

1. 点击输入框下方的提示，弹窗直接显示提示已经拿到的检查结果，不再重新
   检查、不进加载态；结果超过缓存时长时在后台补一次，旧列表保持可见。
   弹窗里每一行右侧是「更新」，页脚是「全部更新」。
2. 单个「更新」只把这一行的名字发给 Host；「全部更新」把列表里的名字一起发
   过去。Host 同样接受省略名字（表示检查得到的全部）。
3. Host 解析工作区后先强制检查一次，把请求里的名字与「确实有更新」的名字
   求交集：已经是最新的、不在 `skills-lock.json` 里的、或有本地修改的名字
   不会传给 CLI。
4. Host 逐个执行 `skills update <name> -p -y`，工作目录是工作区根目录。
   同一个插件实例内的更新串行执行（CLI 会整份重写 lockfile，不能并发）；
   单个 skill 失败不中断整批。
5. 更新结束丢弃该工作区的检查缓存、重新检查一次，把新快照随响应返回。
   弹窗直接用它刷新列表与提示计数，不需要再发一次检查请求；失败的 skill
   会继续留在列表里，并显示失败原因。
6. 全部更新成功、列表为空时，弹窗显示「项目技能都已是最新的」，提示也随之
   消失。只有检查结论确实是「全部最新」才显示这句；工作区没有可检查对象时
   显示「没有可检查的项目技能」并带上原因。
7. 更新在后台进行：发起后可以随时关闭弹窗，请求挂在页面级的更新 store 上，
   不会随弹窗卸载而取消。提示条改成「正在更新 N 个技能」，结束后短暂显示
   「已更新 N 个技能」，再把新快照同步给计数。重新打开弹窗能看到进行中的
   状态与结果；单个 skill 更新时该行显示「更新中…」，批量更新时显示
   「正在更新 N 个技能…」，并注明「更新在后台继续，可以关闭弹窗」。

也可以继续用 [Skills 插件](../skills/README.md) 的页面逐项更新。两个插件用的
是同一个 CLI，更新完都会让下一次检查看到新版本。

## 限制

- 只检查**项目级**技能（工作区根目录的 `skills-lock.json`）。全局技能
  （`~/.agents/skills`）不在这里提示，那是 Skills 插件的页面负责的范围。
- 工作区没有 `skills-lock.json` 时没有可检查的对象；手工安装、没有记录在
  lock 里的技能也不参与。
- 不轮询：进入会话、切换会话时检查一次，之后靠打开弹窗或点「重新检查」刷新。
- 首次检查要访问来源仓库，可能需要几秒到几十秒；检查期间提示不占位置。
- 更新会改写工作区里的 `skills-lock.json` 与 `.agents/skills/` 下的技能目录
  （由 CLI 完成），没有额外的二次确认：点了按钮就执行。本地改过的技能已被
  排除；其余仍建议在更新前确认工作区是干净的。
- 提示位于 `conversation.composer.dock`（输入框卡片下方的统计行），排在
  「上下文已用」圆环之后。没有会话时不渲染；新建会话的空白会话有 id，会
  正常显示。
- 提示只统计「上游有更新」。只有本地修改、没有上游更新的技能不会让提示出现。

## 要求

- DSH `>= 0.2.2-rc.1`。
- 插件随包安装 `skills@1.9.0`；不需要已安装 `@buka/dsh-plugin-skills`。
- Host 需要 `sessions` 服务；`workspaceRegistry` 是可选服务，没有时退回
  会话的 `cwd`。

## 安全

Host 注册两条本机路由，并沿用 DSH web 组合的信任栅栏
（`connection.requestRejection`）：非本机或未认证的请求会被拒绝。

- `GET /skill-update-check/status?sessionId=…&refresh=1`：检查。
- `POST /skill-update-check/update`：更新，请求体是
  `{ sessionId, skills? }`。

浏览器只能传会话 id、`refresh=1` 与 skill 名字，不能传路径——目录完全由 Host
从会话与工作区注册表解析。更新只接受 JSON POST，名字有长度与数量上限；Host
还会把名字与一次强制检查的结果求交集，所以浏览器无法借这条路由更新任意对象。
检查只读；更新以工作区为 cwd 运行 CLI，只改这个工作区的 lock 与技能目录。
响应里的 CLI 输出尾部只用于排查失败。
